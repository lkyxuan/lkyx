# 先搜开源，再动手（Prior Art First）

用户提出一个想法、提案或"我想做一个 X"时，**不要直接写代码**。先花几分钟找现成方案，用调研结果决定：直接用、改造、组合，还是自己写。

## 何时触发
- 用户描述一个要做的产品、功能、工具、脚本、爬虫、自动化流程
- 用户说"我想做 / 能不能做 / 有个想法"
- 不触发：修一个具体 bug、改一行配置、用户明确说"别搜了直接写"

## 第 0 步：先翻自己的笔记
如果项目里有 `docs/notes/`，先看有没有同类需求的调研记录，有就在它的基础上补充。

## 第 1 步：把提案拆成可搜的问题（不超过 5 行）
- 核心要解决的问题是什么（一句话）
- 关键能力拆成 2–4 个关键词组（中英文都写，英文为主）
- 硬约束：语言/运行环境/许可证/是否要自托管/预算

## 第 2 步：多渠道搜索（并行发出）
按顺序覆盖，至少前 4 类：
1. **GitHub 仓库**：`gh search repos "<关键词>" --sort stars --limit 10`，以及 `topic:<词>`；再试 2–3 个同义词
2. **GitHub 代码**：`gh search code "<关键 API 或函数名>"`，找别人写过的小脚本、片段、gist
3. **Awesome 列表**：搜 `awesome-<领域>`，从中挑候选
4. **网页搜索**："<问题> open source"、"<问题> alternative"、"how to <问题> github"；同时看 Hacker News / Reddit / V2EX 讨论
5. **包管理器**：npm / PyPI / crates / Go pkg 搜同名能力的库
6. **官方文档 / API**：目标平台是否已提供官方 API、SDK、导出功能（经常比爬虫更好）
7. **MCP / Claude skill / 插件**：如果是给 Agent 用的能力，搜现成的 MCP server 或 skill

候选多时可以派 1–2 个子 agent 分别跑不同渠道，但只在用户或 CLAUDE.md 允许时这么做。

## 第 3 步：评估候选（每个候选看这几项）
| 项 | 看什么 |
|---|---|
| 匹配度 | 覆盖了需求的百分之多少，缺什么 |
| 活跃度 | 最近一次提交、issue 响应、star 趋势 |
| 许可证 | MIT/Apache 可放心；GPL/AGPL 要提醒；无许可证不能直接拿来用 |
| 体量 | 是轻量库还是重型平台，引入成本多大 |
| 质量信号 | 有无测试、文档、release，依赖是否健康 |
| 合规 | 爬虫类：目标站点 ToS / robots.txt / 是否有官方 API |

不要只看 README，至少打开 1–2 个最佳候选的核心源码确认它真的能用。

## 第 4 步：给出调研报告，然后停下来等用户选
格式（简洁，中文）：

```
## 提案：<一句话>
### 结论
推荐：<复用 X / 基于 Y 改造 / 自己写>，理由一句话。
### 候选
1. <名字>（链接，★数，最近更新，许可证）— 能做什么，缺什么
2. ...
### 三条路
- A 直接用：<怎么用，工作量>
- B 改造/组合：<改哪里，工作量>
- C 自己写：<为什么值得，可借鉴哪些实现>
### 风险
<许可证、维护、合规、ToS>
```

- 如果搜不到合适的，明确说"已搜过 X/Y/Z 渠道，没有合适方案"，并列出可借鉴的局部实现，再进入自己写。
- 用户选定后才开始写代码。

## 第 5 步：记录
把调研结论写进项目的 `docs/notes/<YYYY-MM-DD>-<主题>.md`（格式见 `lkyx-workflow`），下次同类提案先查这里，避免重复搜索。

## 原则
- 搜索是为了少写代码，不是为了拖延：单次调研控制在 10–15 分钟内，候选列 3–5 个即可。
- 自己写不是失败：调研的价值在于知道别人怎么做、踩过什么坑。
- 抓取公开数据前先找官方 API；尊重 ToS 和 robots.txt。

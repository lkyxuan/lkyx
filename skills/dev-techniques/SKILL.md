# 开发技巧

这些技巧都来自 0xmiracle 过往的开发对话，是他反复纠正或主动提出过的做法。只收技巧，不收技术选型。
每条写了**什么时候用**和**怎么做**。新技巧由 `harvest-techniques` 从新的对话里补进来。

## 动手前

### 1. 先看平台自己有没有
- **什么时候**：要做一个功能、页面或数据管道之前。
- **怎么做**：先问"目标平台自带的功能能不能直接满足"。例如要看关注列表，先看平台自己的列表页够不够用，不够再做管理页面；要拿数据，先找平台已经在推送或导出的数据，再考虑抓取。这一步和 `prior-art-first` 一起做。

### 2. 先讲方案，再动手
- **什么时候**：任何超过几十行、或会动外部账号和服务的改动。
- **怎么做**：先用几行话说清楚"准备做成什么样"，用户看过点头再写。用户问"要不要先讨论方案"就说明这一步漏了。

## 做的时候

### 3. 复用已有的环境和登录态
- **什么时候**：需要登录、浏览器、账号、密钥才能验证的场景。
- **怎么做**：优先用用户已经登录好的浏览器窗口、已有的会话和已配置的密钥管理工具，不要另开一个干净环境再让用户重新登录。确实必须隔离时，先说明原因，一次说清楚，不要反复切换。

### 4. 用测试数据摸底，用完就清
- **什么时候**：要在真实平台上试接口、建列表、建资源来摸清行为时。
- **怎么做**：建明显标成测试的资源（如 `test-` 前缀）去试，摸清楚后删掉，再按方案正式做。在交付说明里写明清理了什么。

### 5. 不悄悄降级
- **什么时候**：为了更快、更省而改变用户输入的属性（分辨率、画质、数据量、采样频率等）。
- **怎么做**：默认保持原样。确实要降级，先说代价（慢多少、大多少）再问，不要自己决定。

### 6. 自己验收完再交付
- **什么时候**：交付前。
- **怎么做**：在用户真实的账号、数据、机器上跑一遍完整链路，而不只是单元测试或模拟数据。交付时附上能直接看的证据：截图、预览链接、运行输出。跑不了就明确说哪一段没验证。

### 7. 卡住两三次就换路
- **什么时候**：同一个问题试了两三种改法还是不行。
- **怎么做**：停下来，不要继续在原路上硬试。回头重新搜现成方案或官方文档（`prior-art-first`），或者把卡在哪、试过什么、有哪几条路告诉用户，让用户选。

### 8. 删东西前先核对
- **什么时候**：清理分支、删文件、删云端资源、删数据之前。
- **怎么做**：先列出要删的东西，逐个核对它的内容是不是已经合并、备份或者确实没用了（比如分支是否已通过 PR 合并进主线），把核对结果给用户看，确认后再删。

## 交付时

### 9. 一次交付要让人看得懂
- **什么时候**：每次汇报结果。
- **怎么做**：
  - 第一句说成没成。
  - 然后只说三件事：改了什么、怎么验证的、需要我决定什么。
  - 一次别甩出十几个模块。范围大时拆成几步，每步交付一块；用户说"跟不上""学不动"时，停下来把剩下的拆小。
  - 细节上拿不准的地方，反过来问用户，而不是自己猜着做完。

### 10. 能先跑就先跑，人负责改
- **什么时候**：可撤销的改动（分支、PR、草稿、本地文件）。
- **怎么做**：先做出来让用户看结果再改，不要每一步都停下来等审批。不可撤销的（生产、删除、对外发送）仍然先问。

## 和别的系统、别的 Agent 对接

### 11. 做成独立模块，让别的 Agent 能读懂
- **什么时候**：这块功能以后要接进另一个大系统，或交给另一个 Agent 部署。
- **怎么做**：单独一个仓库或目录，只负责把事情做通；对外给清晰的接口（命令、函数或 HTTP 接口），README 写清楚怎么加配置、怎么取数据。对接方优先调接口，而不是读一大堆文档才知道怎么写。

### 12. 交接时给一段能直接粘贴的提示词，没做完留一页说明
- **什么时候**：工作要交给另一个 Agent 或会话（Hermes、Codex、另一个 Claude）继续，或要问它"做了没有"。
- **怎么做**：写一段自包含的提示词：背景、要做/要查什么、相关仓库和分支、怎么判断完成。用户直接复制过去就能用。
- 工作没做完就要停下时（会话要结束、换 Agent 接手），在项目的 `docs/notes/` 里留一页"做到哪、下一步"：已完成什么、还剩什么、卡在哪、下一步先做什么。

### 13. 多个 Agent 并行时，状态汇报到同一个地方
- **什么时候**：同一个人同时开了很多个会话或 Agent 在跑任务。
- **怎么做**：每个任务在需要用户决定、完成或失败时，都向同一个地方汇报（同一个看板、同一个仓库的任务文件或同一个接口），写清楚"需要你做什么"。不要让用户挨个点开几十个对话去找哪个在等他。

### 14. 好用的小工具单独开源
- **什么时候**：做出了一个和具体项目无关、别人也能用的小脚本或工具。
- **怎么做**：问用户要不要单独放一个 GitHub 仓库公开，附上 README 和安装方法。发布前检查没有密钥、个人路径和账号信息。
